# Pantry acceptance record

**Purpose and minimum outcome.** A US service business replaces QuickBooks Online, Xero or FreshBooks with Pantry. Its owner, bookkeeper and outside accountant keep the books current from live bank and card feeds and captured receipts and bills. They send invoices that get paid by card or ACH, approve and pay bills through a provider, post payroll and processor activity, reconcile, report on the cash or accrual basis, and close each month with only judgment calls left for the accountant. Throughout, they can leave with a restorable archive and an accountant package. The clauses are in [CONTRACT.md](CONTRACT.md).

**Status: 74 of 141 clauses done, 43 partial, 24 missing.** The nineteen ledger-foundation clauses (PAN-01 to PAN-19) are LOCAL PROVEN. Each has one flow test through the public HTTP door of the real Worker on Miniflare, with a real D1 database, every migration applied and genuine native sign-ins (`pnpm run test:pantry`, files under `tests/api/`). The built app is driven in a browser at 1440 and 390 pixels wide (`pnpm run test:app`, `tests/app/`), and backup and restore run through the `rer` verbs on fresh clones exactly as the docs give them (`pnpm run test:restore`, `tests/restore/`). LOCAL PROVEN means exercised locally; it is not hosted, provider, accountant or tax acceptance.

ct’s API-001a and API-001b are recorded as API-001 and API-EGRESS-001 for the pinned parser; these are aliases for the same ruled obligations.

Every other row names its acceptance journey and the test that will prove it. A test marked "(target)" does not exist yet, and its clause stays partial or missing until that test passes through a public door. Provider journeys run against the provider's sandbox or test mode (Plaid, Stripe, Melio, BILL, Gusto, Rippling, Intuit, Xero, FreshBooks, Avalara, TaxJar, Square, PayPal, Shopify, Mercury, Ramp, Jobber, Housecall Pro, ServiceTitan's integration environment, QuickBooks Time, Harvest, IRS IRIS test system), with fakes only at that paid or network edge. Sandbox journeys never establish production access: each provider's production path (CONNECT-001) is proven separately, from a fresh installation, by an owner with no developer accounts.

## Evidence and decision rule

`rer verify` runs every clause's flow test on each push in the Verify workflow; `pnpm run test:app` (in `rer verify`) drives the built app in a browser and `pnpm run test:restore` (its own Verify job) runs backup and restore on fresh clones. A clause is done only while its named test passes on the head being released; a partial or missing clause moves to done when its target test exists and passes through a public door. Status changes are recorded here and in CONTRACT.md's status table in the same change.
